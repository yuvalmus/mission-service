### 1. עקרון האטומיות (All-or-Nothing Execution)

כדי למנוע מצב של חוסר עקביות במידע (Inconsistency), כל עדכון או הוספה של יישות/נתיב והפעולות הנגזרות ממנה (גיבוי היסטורי והתראות בזמן אמת) מבוצעים תחת **טרנזקציה אטומית יחידה**.

ב-PostgreSQL, טריגרים מסוג `BEFORE` ו-`AFTER` מתבצעים **בתוך אותו context של הטרנזקציה** שפתחה האפליקציה:

- אם ה-`UPDATE` בטבלת `entities` מצליח אך טריגר הגיבוי `trg_route_lww_backup` נכשל (או להפך) — מתבצע **`ROLLBACK` מוחלט** לכל הפעולה.
    
- שום שינוי לא נשמר בדיסק (WAL) ולא מופץ ל-`pglogical` / NATS עד לביצוע `COMMIT` מוצלח.

- **עדכונים מרובים באותה פקודה (Batch Updates):** כאשר מתבצע עדכון של מספר ישויות תחת אותה משימה בפקודה אחת, מונה המשימה מוקדם וכל הישויות המעודכנות באותה קבוצה מקבלות את אותו מספר מונה עדכני. הדבר מתאים לחלוטין לקונספט שמדובר במצב המשימה החדש, ושאילתת ה-Delta (`> sinceSeq`) תמשוך בצורה מושלמת את כל הישויות שהשתנו יחד.
    

### 2. זרימת הטרנזקציה והטריגר (Execution Lifecycle)

```
[ Application / Backend Service ]
              │
              │  1. BEGIN TRANSACTION
              ├────────────────────────────────────────┐
              │                                        │
              │  2. UPDATE entities SET ...            ▼
              │                             [ PostgreSQL Engine ]
              │                                        │
              │  3. Execute Backup Trigger             │
              │     (trg_route_lww_backup)   │
              │     - Copies OLD to `route_backups`    │
              │     - Enforces 10 backup limit         │
              │     - Increments version & timestamp   │
              │                                        │
              │  4. Execute Notify Trigger             │
              │     (trg_entities_notify)              │
              │     - Fires `pg_notify('entity_changes')`
              │                                        │
              │  5. COMMIT TRANSACTION                 │
              │ ◄──────────────────────────────────────┘
              │
    [ Changes Committed to WAL ]
              │
              ├───────────────────────┐
              ▼                       ▼
    [ pglogical Replication ]    [ LISTEN / NOTIFY Service ]
```

### 3. סדר הפעלת הטריגרים בעת עדכון יישות/נתיב

כאשר מבוצעת פקודת `UPDATE` או `INSERT` על טבלת היישויות (`entities`), מופעלים הטריגרים בסדר טורי מוגדר:

#### א. טריגר גיבוי ואכיפת גרסאות (`trg_route_lww_backup`)

- **תפקיד:** שיוך הגרסה הישנה ליומן הגיבויים, קידום אטומי של מונה המשימה (`missions.last_change_seq`) עם Row Lock קצר להבטחת רצף מספרי מושלם ללא Gaps, וקידום ה-`version` של היישות.
    
- **תזמון:** `BEFORE INSERT OR UPDATE ON entities FOR EACH ROW`.
    
- **מנגנון הנעילה:** הטרנזקציה נועלת לזמן קצר מאוד (שורת Row Lock יחידה בטבלת `missions`) את המשימה הרלוונטית בזמן ה-UPDATE המקדם את המונה, מה שמבטיח שאין התנגשויות או פערי רצף בתוך אותה משימה.

    

#### ב. טריגר התראה בזמן אמת (`trg_entities_notify`)

- **תפקיד:** שידור התראה אסינכרונית לרכיבי המערכת המאזינים ב-Pub/Sub.
    
- **תזמון:** `AFTER INSERT OR UPDATE ON entities FOR EACH ROW`.
    
- **לוגיקה:** מפיק הודעת JSON רזה המכילה מזהים וגרסאות בלבד (`entity_id`, `mission_id`, `version`, `last_change_seq`, `origin_node`), ומפעיל `PERFORM pg_notify('entity_changes', payload)`.
    

### 4. דוגמת מימוש ברמת האפליקציה (C# / Node.js Pattern)

האפליקציה פותחת טרנזקציה מפורשת ומבצעת עדכון ישיר על הטבלה הראשית. כל שאר הטיפול בגרסאות ובגיבויים מתבצע דטרמיניסטית בתוך ה-DB:

TypeScript

```
import { Client } from 'pg';

async function updateEntity(client: Client, entityData: EntityUpdateInput) {
    try {
        await client.query('BEGIN');

        // עדכון היישות הראשי - ה-Triggers ב-DB כבר יגבו את ה-OLD ויפיצו pg_notify
        const updateQuery = `
            UPDATE entities 
            SET 
                properties = $1,
                geometry = $2,
                origin_node = $3
            WHERE id = $4
            RETURNING id, version;
        `;

        const values = [
            entityData.properties,
            entityData.geometry,
            entityData.originNode,
            entityData.id
        ];

        const result = await client.query(updateQuery, values);

        await client.query('COMMIT');
        return result.rows[0];

    } catch (error) {
        await client.query('ROLLBACK');
        throw new Error(`Failed to commit entity update: ${error.message}`);
    }
}
```

### 5. התנהגות בעת סנכרון רשת (`pglogical`) ומודל LWW

כאשר עדכונים מגיעים משרת אחר בעת החזרה מנתק רשת או במהלך עבודה שוטפת באמצעות `pglogical`:

1. **החלת שינויים ישירה:** השינויים מוחלים ברמת ה-WAL replication ישירות על טבלת `entities`.
    
2. **מניעת שכפול כפול של גיבויים:** טבלת הגיבויים `route_backups` משוכפלת אף היא ב-Mesh. כדי למנוע יצירת רשומות גיבוי כפולות עבור אותו עדכון, טריגר ה-`BEFORE UPDATE` מוגדר לפעול ברמת **המקור בלבד** (`session_replication_role <> 'replica'`). השרת המקבל אינו יוצר שורת גיבוי נוספת אלא קולט את שורת הגיבוי המקורית שהגיעה מהרשת.
    
3. **הפצת התראות UI מקומיות:** טריגר ה-`AFTER UPDATE` (`trg_entities_notify`) משדר התרעת `pg_notify` ל-Frontend המקומי כדי לרענן את תצוגת המפה בזמן אמת עם המידע שהתקבל מהרשת.
